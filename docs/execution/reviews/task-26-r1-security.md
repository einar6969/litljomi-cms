## Deferred Minor (Task 18 row: 10a–10c and the client)

  - A body with a BOM prefix, or an invalid byte signed as U+FFFD, gets 401. The same bytes signed as bytes get 200 (new SDK test).
  - The string|Uint8Array widening is safe. `signWebhook` now calls `update(`${ts}.`,'utf8').update(body)`, and a string body is hashed as UTF-8 (Node's default), so it produces the same bytes as before and existing signers stay compatible.
  - `verifyWebhook` accepts only `string` or `instanceof Uint8Array`. Anything else, including a Uint8Array from another realm, returns false (fails closed).
- **10b, cheap checks first: holds as ordering.**
  - The timestamp format `^\d{1,15}$`, the signature format `^[0-9a-f]{64}$` and the 300-second tolerance are all checked before `secrets()` or the body is touched (spy test: `bodyUsed` stays false and `secrets` is not called).
  - The comparison is constant-time: every secret is compared with `timingSafeEqual` on equal-length buffers, and the loop does not stop at the first match.
  - Rotation works: both secrets are accepted in the e2e test, and empty or non-string secrets are skipped. An empty list gives 401.
  - Header edge cases all gave 401: a leading space, `ts.0`, uppercase hex, a leading zero, and a timestamp 299 seconds in the future with a bad signature.
  - These checks do not stop an attacker, though. See F2.

## Findings

**[Minor] F1, `apps/demo-site/e2e/fixtures/generate.ts:45` and `apps/demo-site/e2e/fixtures.test.ts:20-24` (point a).**
- The fixture computes `contentHash(r.data)`.
- §7.2 and Task 20 step 3 define the hash over the entry's complete projected record minus the `contentHash` field.
- The test name "carries the real content hash of each entry record" states the wrong contract.
- No security property depends on it today:
  - Sites only echo the hash.
  - Task 20 tests its own recomputation independently.
  - Task 21's end to end uses the real worker.
- Still, it is an oracle that later fixture-based work (for example Task 27's "fixture bundle served locally") could copy. The fixture would then accept a hash that does not change when slug, title or sortAt change.
- Recommendation: hash the complete record minus `contentHash`, with the same helper Task 20 uses, or rename the test so it makes no claim about the contract.

**[Minor] F2, `packages/sdk/src/revalidate-handler.ts`, the `req.arrayBuffer()` line (oversize bodies; outsider-reachable, so rated under the full standard).**
- The cheap checks can be satisfied by anyone (any 64 lowercase hex characters plus the current time), so they bound nothing. The handler then buffers the whole body and computes one HMAC over it per secret, with no size cap, although the real payload is about 15 bytes.
- Measured locally with 2 secrets (Node 22.23.1). "Memory" is the measured growth in Node's arrayBuffers, not a strict peak.

  | Body | Status | Time | Memory |
  |---|---|---|---|
  | 4.5 MB | 401 | 14.8 ms | +11 MB |
  | 100 MB | 401 | 112.7 ms | +182 MB |
  | 500 MB | 401 | 656.7 ms | +700 MB |

- Why Minor and not Major:
  - §2.2 places sites on Vercel, whose 4.5 MB function request-body limit holds this to about 15 ms and 11 MB per request, well under the 100 MB and 5 s bounds.
  - The effect is limited to one site and does not reach another tenant.
- Under a self-hosted `next start`, which the spec does not use for sites, it would be above the bound and Major. This makes the rating contingent on hosting.
- Recommendation: before reading the body, reject a `content-length` above a small cap (for example 64 KiB), and stop reading a streamed body at that cap. The SDK then no longer depends on the platform's limit.
