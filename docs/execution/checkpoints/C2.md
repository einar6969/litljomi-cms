## Unresolved issues (for your decision)

1. **Spec §7.4 vs the plan: delivery retries.** §7.4 says retries "use exponential backoff for up to 24 hours". The plan's Task 21 text and decision 35 specify a fixed interval in M1 (one retry per sweep, up to 10 attempts), which is implemented. Options: amend §7.4 to name the M1 fixed interval, with backoff later (recommended; the sweep runs every minute, so 10 attempts span ≈10 minutes); or implement backoff now.
2. **A release stuck in `building`.** A worker killed mid-build (e.g. by `maxDuration`) leaves the release `building` forever; every later build of that tenant, unpublishes included, returns `busy`, and nothing in M1 recovers it. Recommended: a sweep step that fails a `building` release older than the worker's maximum duration (a new `service_role` function), in Phase 4 or as a small follow-up before Task 25.
3. **Failed builds leave public objects nothing records** (a bundle uploaded before a later step failed, copied media). No new exposure in M1, but M3 retention (§7.2) cannot find them. Recommended: record uploaded paths in the failed release's error when M3 retention is built.
4. **Whole-tenant build failures:** a permanently unreadable previous bundle, or an asset whose private file is missing (only an editor in their own tenant can cause it), fails every build of that tenant, which is broader than §7.1's "one failing entry does not block the tenant". Recommended: treat a per-asset copy failure as an omission of the entries that reference it.
5. **Entries with no declared checks are confirmed live with nothing checked** (types without site integration; an unpublish of an entry the previous delivered release did not contain). This matches §7.4's wording. Recommended: accept for M1 and say so in the spec's "Limits".
6. **The marker parser and author-written HTML:** script double-escaping and quoted attributes on end tags can give a false `absent` or `present`, only from raw HTML the site author writes (editor text cannot, as React and Next escape it). Recommended: accept and document in §7.3 that sites must not render raw markup around entry markers.
7. **Precedent:** the local end to end's shell script (`tests/integration/scripts/cms-next.sh`) reads the local stack's secret key at run time outside the lint-protected folders (loopback only, never written or echoed). Recommended: accept for local tests only.
8. **Hosted check for Task 28:** `alter role service_role set statement_timeout` worked locally through supautils; whether hosted Supabase allows it on its reserved role is unproven until G3.
9. **Stricter than the spec, for the record:** an `absent` check on a page other than the entry's own path must answer 200, and an own-path 404 that cannot be scanned to its end fails. Both fail closed.

**To watch it yourself, step by step** (leave the database as the run above left it, or run it once first so a demo release exists):

1. Start the CMS worker on port 3100 (it reads the local keys from `supabase status`; the two secrets are throwaway local values):

```bash
CMS_INTERNAL_SECRET=local-internal CRON_SECRET=local-cron CMS_PUBLIC_URL=http://localhost:3100 sh tests/integration/scripts/cms-next.sh dev -p 3100
```

2. In a second terminal, build and start the demo site on port 3101 (the seeded demo site's URL and webhook secret; the build cache is cleared because local release numbers restart after a reset):

```bash
cd apps/demo-site && rm -rf .next && CMS_DELIVERY_BASE_URL=http://127.0.0.1:54321/storage/v1/object/public/delivery CMS_TENANT=demo CMS_WEBHOOK_SECRETS=s3cr3t CMS_MEDIA_HOST=media.example.test NEXT_TELEMETRY_DISABLED=1 pnpm build && CMS_DELIVERY_BASE_URL=http://127.0.0.1:54321/storage/v1/object/public/delivery CMS_TENANT=demo CMS_WEBHOOK_SECRETS=s3cr3t CMS_MEDIA_HOST=media.example.test pnpm start
```

3. Open http://localhost:3101/events and http://localhost:3101/events/x; "View source" shows `data-cms-entry` and `data-cms-hash` beside the event.

4. In a third terminal, run the sweep the way Vercel Cron will (it processes pending requests, builds, notifies the site and live-checks):

```bash
curl -i -H "Authorization: Bearer local-cron" http://localhost:3100/api/cron/sweep
```

5. Watch the delivery states (`notify_status`, then `live_status` reaching `ok`):

```bash
docker exec supabase_db_litljomi-cms psql -U postgres -c "select r.number, r.status, d.notify_status, d.live_status, d.live_confirmed_at, d.last_error from cms.site_deliveries d join cms.releases r on r.id = d.release_id join cms.tenants t on t.id = r.tenant_id where t.slug = 'demo' order by r.number desc limit 5;"
```

To publish a new version of `/events/x` and watch it go live, run `pnpm test:e2e-local` again in another terminal while you watch steps 3 and 5; it saves a new draft, publishes it through the worker route and waits for `live_status = 'ok'`. (Note that it starts its own copies of the CMS and the demo site, so stop the ones from steps 1–2 first, or the demo site's port 3101 will be busy.) Stop everything with Ctrl-C, then:

```bash
pnpm db:stop
```
