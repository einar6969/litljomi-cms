### Issues found, open

1. **Storage CDN serves the old pointer past its max-age (root cause of A6/A7/criterion 2).** With 48, 48.1 and 48.2 in place, a blocking regeneration of `/events` at 08:02:38, 33 s after `demo/current.json` was overwritten, still rendered the previous release. The public URL's CDN keeps `current.json` longer than `cache-control: public, max-age=30`; how long is not measured. Every test that passed (releases 3, 5, 7, 9) did so because the CDN happened to be fresh at the first read. **Recommended fix (not built):** the worker notifies a site only once the pointer's public URL serves release N (bounded polling, the lag logged per publish), so the live window opens after the CDN is fresh. CMS code only. Alternatives: a later resend (unmeasured lag) or a cache-busting pointer read in the SDK (SDK and spec change).
2. **Plan/spec conflict, resolved for the demo site only.** §7.3 says `revalidateTag('cms')` (immediate); plan Task 26 said `'max'` (stale-while-revalidate, so one webhook regenerates from the cached pointer). Fixed in the demo site (48.2, and the plan's Task 26 line amended). **LABAK's `hub-integration` route is unchanged** and very likely uses `'max'` too: changing and pushing it is a G7 action awaiting Einar.
3. **`not_confirmed` is final.** After a missed live check the site keeps the old pointer until the next publish of that tenant (no retry by design, `worker_deliveries_to_retry`). Unchanged; with issue 1 fixed it should rarely trigger, but a missed check still leaves a stale site.
4. **Pushes start failing Vercel preview builds.** Every push of `m1/phase-1` started Git preview deployments on `vefumsjon-staging` and `demo-staging`, which fail (`CMS_MEDIA_HOST is not set`: previews have no variables). Production is unaffected. To decide: an Ignored Build Step for non-production branches (as on `landssamband-bakarameistara`), or preview variables.
5. **The live check gives no evidence of the resend.** Neither the worker nor the sites log a successful resend, and Vercel runtime logs show only errors, so each resend was inferred from code and cache timing. A single info log line per resend (and per live-check result) would make the next run provable.
