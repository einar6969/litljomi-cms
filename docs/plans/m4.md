# M4 Operations: implementation plan

> **Status: APPROVED by Einar on 2026-11-05 ("Approve plan", decision 58).** Hosted steps need their own approval, under "Hosted acceptance".

**Goal:** make the Hub operable by one person, with the smallest implementation that passes M4's two acceptance tests.

**Sources.** `docs/architecture.md` §13.2 (M4 row) and the sections each task cites; decisions 50 and 53 to 58 in `docs/plans/2026-11-01-m0-m1.md`; `docs/king/OPEN-ISSUES.md`, section M. If this plan and the spec disagree, the spec wins: stop and report it.

**M4 delivers (§13.2):** a read-only platform console; an idempotent provisioning CLI; secret rotation; tenant suspension and editor revocation from the CLI; runbooks.

**M4 is accepted when (§13.2):** a fresh tenant is provisioned from the runbook in under an hour, and a webhook secret is rotated without failed deliveries. Both run on staging.

**Out, by decision:** nightly and on-demand exports (53, 56), restore (55), offboarding (53). Don't add anything back, and don't grow the console beyond this plan.

## Global constraints

- Next.js 16.4.3, React 19.3.1, TypeScript 6, Zod 4, Supabase JS 2.118, Node 22, pnpm 11. No new runtime dependency.
- All `api` functions and views are invoker: `SECURITY INVOKER` or `security_invoker = true`, with `search_path = ''` on functions. No `SECURITY DEFINER`.
- `admin_*` is executable by `service_role` only. Errors use `raise exception` with `P0001`: `not_found`, `slug_taken`, as decision 3 lists; bad input uses `22023`.
- The console uses the signed-in admin's JWT and never the Supabase secret key. No platform-admin clause on content tables (§4.5).
- Secrets come from standard input only, and never appear in output, logs or chat. Einar enters every key.
- No tenant slug literal in core (`pnpm check:slugs`).
- Console copy is English: it has one reader, and this adds no Icelandic strings to approve.

## How a task runs

Local, per decisions 53 and 54. One task, one branch `m4/<task-id>-<slug>`, one PR. A fresh `cms-implementer` works test-first and doesn't merge. A fresh `cms-spec-reviewer` reviews every task, with `cms-security-reviewer` beside it where marked, then `cms-quality-reviewer`. The PASS goes on the PR as `Review: PASS <full sha>` for the exact head. The branch must be up to date with `main` and CI green on that commit, and the KING merges with no further approval (decision 61).

Before a PR opens, these pass locally: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm db:test`, `pnpm test:integration`. Run `pnpm db:reset` first: the local stack is one migration behind.

Docs-only work is a local commit with no PR (decision 54). Local docs commits and the approved `.claude/settings.json` diff reach GitHub in M4-01's PR, and its review covers them.

## Review focus

The failures most likely to bite, each pinned to a test in the task that owns it:

1. **Rotation done out of order or with a mistyped value:** the site refuses the webhook, the delivery retries, and it succeeds once the site has the new secret (M4-02).
2. **A rerun after a partial failure,** such as a dropped connection between the invitation and the membership: a rerun finishes the job and creates no duplicate (M4-02).
3. **The wrong person reaches the console:** an editor, a signed-in outsider, or an admin at `aal1` gets no operational rows, whatever the page does (M4-03, M4-04).
4. **Suspending a tenant with work in flight:** a pending request is refused, the site keeps serving its last release, and reactivating restores publishing (M4-01).
5. **Revoking an editor who has a tab open:** the next save is refused and the editor loses no local work (M4-01).

## Tasks

### M4-01: Admin functions and suspension audit

- **Spec:** §4.6, §4.7, §8.2, §8.4, §4.5; decision 53.
- **Files:** create `supabase/migrations/20261105100000_m4_admin.sql` and `supabase/tests/database/113_m4_admin.test.sql`. Modify `supabase/tests/database/*` only where a catalog test lists functions.
- **Scope:**
  - `api.admin_set_webhook_secret(p_site_id uuid, p_webhook_secret text) returns void`: as `admin_set_preview_secret`, at least 32 characters (`22023`), lock the site, `vault.update_secret` on `webhook_secret_ref`. `not_found` for no such site or no Vault row.
  - `api.admin_set_tenant_status(p_tenant_id uuid, p_status text) returns void`: `active` or `suspended` (`22023`), `not_found` for no such tenant.
  - `api.admin_remove_membership(p_tenant_id uuid, p_user_id uuid) returns void`: `not_found` for no such tenant; removing an absent membership is a no-op, as `admin_add_membership` is on a duplicate.
  - `api.admin_create_tenant`: returns the existing id when the slug exists with the same name; `slug_taken` when the name differs.
  - An audit trigger on `cms.tenants` for a `status` change, action `system.tenant.status_changed`.
- **Acceptance (pgTAP and integration):** each function is refused for `anon` and `authenticated` and runs for `service_role`. After a rotation, `api.worker_sites` returns the new secret, and `webhook_secret_ref` is unchanged. A short secret and an unknown id are refused, with no change. Create-tenant twice with the same name gives one row and the same id; a different name gives `slug_taken`. A status change writes one audit row; a name change writes none. A suspended tenant's pending request is `rejected` with `tenant_inactive`, its public `current.json` is untouched, and after `active` a new request publishes (focus 4). After removal, `save_draft` by that editor fails and an audit row is written; the editor's unsaved-work path is covered by the existing session-expiry test, extended to a refused save (focus 5).

### M4-02: CLI: rotation, suspend, revoke, safe reruns

- **Spec:** §8.2, §8.4, §9.2 ("CLI, idempotent"); decisions 44 and 32.
- **Files:** modify `tools/cli/src/provision.ts` and `tools/cli/src/__tests__/provision.test.ts`. Add a local rotation test to the worker's integration tests.
- **Interfaces:** consumes M4-01's functions. Produces these commands, all with `--expect-ref <ref> [--env-file=<path>]`:
  - `provision webhook-secret --site-id <uuid>`, with the secret on standard input only, using `readSecret` and `SECRET_RE`.
  - `provision tenant-status --tenant-id <uuid> --status active|suspended`.
  - `provision remove-editor --user-id <uuid> --tenant-id <uuid> [--tenant-id <uuid> ...]`.
- **Scope, safe reruns:**
  - `provision tenant` prints the existing id and exits 0 on the same name.
  - `provision site` on an existing base URL prints the site id, says the secret was not changed, and exits 0.
  - `provision editor --email` for an existing user finds the id through the Auth admin users list and adds the memberships.
  - `Api` gains a guarded GET for that lookup, under the same origin, redirect and redaction rules.
- **Acceptance (unit, with a fake fetch):** each command's request and its refusals; no output contains the key or either secret; a terminal on standard input is refused. A rerun after each partial failure finishes with no duplicate (focus 2). **Integration:** the full rotation against a local site: accept `old,new`, rotate, publish, then accept only `new` and publish again, with no failed delivery. With the site holding only `old`, the delivery retries and then succeeds once the site accepts `new` (focus 1).

### M4-03: Console read surface

- **Spec:** §4.5 ("Console reads"), §8.4, §8.5 (persona matrix), §2.1. Needs the spec amendment below.
- **Files:** create `supabase/migrations/20261105110000_console_views.sql`, `supabase/tests/database/114_console_views.test.sql` and `tests/integration/src/console-views.test.ts`.
- **Interfaces:** produces `security_invoker` views in `api`, `SELECT` for `authenticated` only:
  - `console_admin(user_id)`: the caller's own `platform_admins` row, at any `aal`.
  - `console_tenants`, `console_requests`, `console_releases`, `console_sites` (non-secret columns), `console_deliveries`, `console_audit`.
  - All but `console_admin` also filter on the caller being a platform admin at `aal2`, so an editor's own rows don't appear.
- **Acceptance:** persona matrix over every view: anon refused; editor, outsider and revoked get nothing; admin at `aal1` gets only `console_admin`; admin at `aal2` sees all tenants. No view exposes a `*_secret_ref` column. No content table gains a platform-admin clause. Each view is `security_invoker` (focus 3).

### M4-04: Console access and TOTP

- **Spec:** §2.1, §4.4 ("console access requires `aal2`"), §8.1.
- **Files:** create `apps/cms/src/app/console/layout.tsx`, `apps/cms/src/app/console/mfa/page.tsx`, `apps/cms/src/app/console/mfa/actions.ts`, `apps/cms/src/lib/console-access.ts` and `apps/cms/e2e/console.spec.ts`.
- **Interfaces:** consumes `api.console_admin`. Produces `consoleAccess(): Promise<'none' | 'needs_mfa' | 'ok'>`: `none` with no `console_admin` row; `needs_mfa` at `aal1`; `ok` at `aal2`, from `auth.mfa.getAuthenticatorAssuranceLevel()`.
- **Scope:** `none` answers 404, as an unknown tenant does. `needs_mfa` goes to `/console/mfa`, which enrols a first TOTP factor (QR and manual code) or challenges an existing one. The page never shows a factor's secret again after enrolment. Uses the signed-in client only.
- **Acceptance (e2e, local):** an editor gets 404 at `/console`; an admin at `aal1` lands on `/console/mfa`, enrols with a code computed in the test helper using `node:crypto`, and reaches `/console`; a wrong code is refused. A later session asks for the code. The Auth hook still refuses a password sign-in.
