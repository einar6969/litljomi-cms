## Tasks

### M3-01: CI pulls Supabase images from `ghcr.io`

- **Spec:** §8.5 ("pgTAP via `supabase test db` against a local stack in CI"); decision 50.4 (CI hit Docker Hub's rate limit on 2026-11-03); decision 50.5 (pass 2's setup script set no registry: the CLI fell back to `ghcr.io` because Amazon's registry could not be reached).
- **Scope:** **this task changes `.github/workflows/ci.yml`** (the `database` job only): Supabase CLI 2.121.0 pulls its images from `ghcr.io` through the CLI's own registry setting. The thread finds that setting in the CLI's documentation or source for 2.121.0 and cites it (link and version) in the pull request; if the CLI has no such setting, it stops and says so. Nothing else in CI changes; action SHAs stay pinned; no new secrets or permissions.
- **Acceptance:** the `database` job on the pull request pulls from `ghcr.io` (its log shows the registry) and runs `pnpm db:test` and `pnpm test:integration` green; the job's permissions stay `contents: read`.

### M3-02: Exponential retries for 24 hours

- **Spec:** §7.4 ("exponential backoff for up to 24 hours … When the attempts run out, the platform admin is alerted … the editor sees delivery failed. A newer release supersedes pending work"), §6.3 (`failed` retried by the sweeper up to a limit), §8.4.
- **Scope:** a migration replaces the fixed schedule (one retry per sweep, 10 attempts) with exponential backoff capped at 24 hours from the first failure, for release builds and site notifications: a `next_attempt_at` on the retried rows, `worker_deliveries_to_retry` (and the build retry path) select by it; a newer release still supersedes. `apps/cms/src/privileged/worker/sweep.ts` and `deliver.ts` follow it.
- **Acceptance:** pgTAP: schedule values (1 min, 2, 4 … capped), exhaustion after 24 hours, supersession, `worker_*` still executable only by `service_role` (catalog); worker unit tests with a fake clock; an integration test: a site answering 500 is retried on schedule and marked failed after the window (time simulated through the function's clock parameter or a test-only setting, not real waiting).

### M3-03: Retries after `not_confirmed`

- **Spec:** §7.4 (live check, re-send, "live not confirmed"); C4 sitting-5 issue 3 and go-live item 19 (`not_confirmed` is final today, so a stale site stays stale until the next publish); decision 50.4.
- **Scope:** a `not_confirmed` delivery is retried on M3-02's schedule: re-notify, then a full live check, until it passes, a newer release supersedes it, or the 24 hours run out (then `failed` and an alert). The editor sees "live not confirmed, retrying" until then (copy draft). Migration as needed for the state; listed.
- **Acceptance:** pgTAP for the new transitions; worker tests: a stale page that becomes fresh on the second attempt ends `ok`; a newer release stops retries of the older; integration on the local stack with the demo fixture site serving a stale pointer for the first check.

### M3-04: Alerts by email

- **Spec:** §8.4 ("worker failures and exhausted retries alert the platform admin … by email from M3"), §10.1; deferred Minor Task 19 quality (repeated alerts on every re-claim).
- **Scope:** an alert sender in the privileged zone; one email per incident, deduplicated across re-claims and sweeps; the audit-log and server-log alerts stay. The hosted transport is **SendGrid**, already set up for litljomi.is (decision 50.5), configured by environment (SMTP host, user and key); local tests send to the local stack's Mailpit with the same code path. No key in the repository or the thread; Einar enters the hosted key in local acceptance.
- **Acceptance:** unit tests for deduplication; an integration test: an exhausted retry sends exactly one email to Mailpit with tenant, release and reason, and no secret or content body.

### M3-05: Failed-entry fallback rules

- **Spec:** §7.1 ("One failing entry does not block the tenant, and fallback fails closed", conditions 1 and 2; "Withdrawal always wins"), §7.4 ("delivery failed for this entry"), §8.5 Delivery rows on fallback.
- **Scope:** the release build reuses an entry's previous projection only when the published `revision_id` equals the previous projection's and every asset and entry it references is still allowed; otherwise the entry is omitted; either way the release proceeds, records the entry in `releases.error`, alerts, and the editor sees "delivery failed" for it. Replaces M1's always-omit rule.
- **Acceptance:** worker tests and an integration test per §8.5 row: fallback never includes an unpublished, archived or never-published entry; refused when `revision_id` differs; refused when a referenced asset is archived or a referenced entry unpublished; an omitted entry's page returns 404 on the demo fixture site.

### M3-06: Retention and public-media cleanup

- **Spec:** §7.2 (Retention: current and previous release only; one hour after delivery delete the one before, with public media referenced only by deleted releases), §5.6 (Withdrawal), §8.4; deferred Minor Task 20 security r1 (a failed build's bundle and media at unrecorded public paths).
- **Scope:** a migration records every public object a build writes (bundle and media paths) before writing it; a sweeper step deletes release files older than the previous release one hour after the newer delivery, and public media no remaining release references, including objects of failed builds. `worker_*` functions for listing and marking deletions; Storage deletes through the worker only.
- **Acceptance:** pgTAP for the new functions and grants; integration on the local stack: after three releases and an hour of simulated time, only releases N and N−1 remain in `delivery`; an image unpublished in N−2 is gone from `media-public` and answers 404; a failed build's objects are removed; an image still referenced is kept.

### M3-07: Private-media orphans and asset-function locks

- **Spec:** §5.6, §4.5, §4.6; deferred Minors Task 24 security r1 (refused or unregistered originals stay in `media-private`; `register_asset` trusts editor-declared metadata; no `tenant_inactive` check in the database), P4 follow-up security r1 (tenant status read without `FOR SHARE`; a suspended tenant's member can upload an orphan).
- **Scope:** a migration: `register_asset` and `update_asset` lock the tenant row `FOR SHARE` and refuse an inactive tenant; a worker sweep removes `media-private` objects with no `assets` row after a grace period; at publish the worker re-derives `width`, `height`, `mime`, `bytes` and `sha256` from the private object it already reads when copying it, and the asset fails validation on a mismatch (decision 50.5: editor-declared metadata is a gap in trust).
- **Acceptance:** pgTAP persona cells for the changed functions; integration: an unregistered upload is removed after the grace period and a registered one is kept; a suspended tenant's `register_asset` is refused; an asset registered directly through `api.register_asset` with false dimensions or MIME type is refused at publish, and the entry is not committed.

### M3-08: Pointer lag recorded per release

- **Spec:** §7.4, §11.1 A6; decision 49.1 (the worker waits until the public pointer serves release N); `m1-report.md` (measured lag 0.6–54 s, "Known limitation"); go-live list ("the pointer lag").
- **Scope:** the worker stores each release's pointer lag (write to first fresh public read, or "bound reached") in `releases` through a `worker_*` function (migration), and the platform view shows it per release. The lag stays a measured limitation (decision 50.5: the CDN ignored the 30 s setting, so shortening it would not help, and the worker already waits it out): no change to the pointer's `max-age` or the SDK's pointer read.
- **Acceptance:** pgTAP for the column and function grants; worker test with a fake public fetch: lag stored at 0 s, after a delay, and as bound reached; integration: a local publish records a lag.

### M3-09: Webhook verification hardening and the stale-hash re-send

- **Spec:** §7.3 item 2 (HMAC and a timestamp within 5 minutes), §7.4 (re-send on stale hash within the same 60-second window), §8.5 Delivery row ("a `present` check fails while the page shows the old hash, even when the layout's release marker is newer"); deferred Minor Task 27 security (`CMS_WEBHOOK_SECRETS.split(",")` without trim; replay within 300 s).
- **Scope:** `packages/sdk`: the secret list is trimmed and empty entries refused; a replayed request within the 5-minute window is accepted as harmless (decision 50.5: revalidation is idempotent and changes nothing) and documented in the handler; no nonce store. Worker: the re-send rules from decisions 48–49 are covered by named tests against §7.4's wording.
- **Acceptance:** SDK tests (spaces around secrets, empty entry, expired timestamp, wrong signature); worker tests for the re-send and for a newer release marker never satisfying `present`.

### M3-10: Preview token route and preview secrets

- **Spec:** §7.5 (token route in `privileged/`, editor's own JWT confirms read access, HMAC with the site's preview secret over `{tenant, entry_id, draft_version, exp}`, 10 minutes), §8.2 (secrets), §8.5 Escalation ("obtaining a preview token for another tenant's entry"), A9; deferred row 28 Step 0 (preview secret not created).
- **Scope:** a migration stores a preview secret per site in Vault, created with the site (`api.admin_create_site`) and readable only on the privileged path; `/api/preview-token` verifies the session, reads the entry with the editor's JWT, mints the token. Editor routes never see the secret.
- **Acceptance:** pgTAP: secret unreadable by `authenticated`, readable by `service_role` (A9 locally); integration: an editor of tenant B cannot obtain a token for tenant A's entry (persona and escalation suites), a non-member cannot, an expired session cannot; token fields and expiry tested.

### M3-11: Preview endpoint

- **Spec:** §7.5 (`/api/preview/{tenant}`: verify the token, return published content overlaid with that draft, projected like a release, media as short-lived signed URLs, never cached), §13.2 ("preview … is never cached").
- **Scope:** the privileged endpoint; the response carries only data scoped by the verified token; `cache-control: private, no-store`; a token for tenant A on tenant B's path is refused.
- **Acceptance:** integration on the local stack: overlay correctness (the draft replaces its published version, other entries unchanged), wrong tenant, tampered and expired tokens refused, the response headers forbid caching, signed media URLs expire.

### M3-12: Preview in the SDK, the demo site and the editor

- **Acceptance:** SDK tests (token verification, draft mode only after a valid token); a local end-to-end test: preview a demo draft and see its content; the published page unchanged for a normal visitor.

### M3-13: SDK on Next.js 15 and 16

- **Acceptance:** `pnpm test` runs the SDK suite against Next.js 15 and 16; both fixture builds succeed locally and pass a local publish-to-live check.

### M3-14: Sign-in hardening

- **Spec:** §4.4, §8.1; deferred Minors Task 32 security r1 (token hash in the GET query string reaches logs and history; "Halda áfram" can swap a session), Task 32 spec r1, C3 follow-up CMS security (proxy refresh on the confirm POST untested, `favicon\.ico` matcher lacks `$`, one Auth `getUser` per confirm GET).
- **Scope:** the confirm page drops the token hash from the address bar after load; when a session exists, it shows which account the link signs in to and asks before replacing it (copy draft); the matcher fix and a proxy-refresh test.
- **Acceptance:** unit and integration tests for each; the existing sign-in tests stay green.
