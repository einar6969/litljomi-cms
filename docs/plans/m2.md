**Sources.** `docs/architecture.md` §13.2 (M2 row), the sections each task cites, LABAK's go-live list (`docs/execution/checkpoints/C4.md`) and the open rows of `docs/execution/deferred-minors.md` that belong to M2. Where this plan and the specification disagree, the specification wins: the thread stops and says so.

**M2 delivers (§13.2):** all v1 field kinds; singletons and editor structure; list search and status filter; conflict-resolution UX; restore from revision; schema evolution (transforms, outdated-draft handling, snapshot check); focal point and alt-text editing; Icelandic copy throughout.

The hosted parts are in "Local acceptance" at the end, run by the local controller under its gates, never by a cloud thread.

## How a task runs

- One task per Claude Code Project cloud thread, one pull request into `main` (decision 50; the Project instructions are in `docs/execution/environment.md`). Branch `m2/<task-id>-<slug>`, title `<task-id>: <summary>`. Einar merges.
- **Checks before the pull request:** `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm db:test`, `pnpm test:integration`, all on the local stack. A task's "Acceptance" lists the tests it adds; they run inside those commands unless stated.
- **Playwright e2e** (`pnpm --filter cms e2e …`) may be written by a task, but cloud threads are not required to run it (see open question 1); it runs in "Local acceptance".
- **`security`** marks a task whose pull request gets the `security` label (it touches RLS, grants, `api`/`worker_*` functions, auth, storage, preview tokens, webhooks or the SDK's verification). Its review checks the plan's 14-item security checklist (M0–M1 plan, "Security-sensitive tasks").
- **Migrations** only where the task says so, listed in the pull request. New Icelandic strings are drafts for Einar, listed in the pull request.
- **Parallel tasks** have no dependency on each other and may run at the same time. They may still both touch a shared file (the field registry, `i18n/is.ts`); the second to merge brings `main` into its branch with a merge commit (never a rebase: force-pushing is not allowed).

### M2-03: Scalar field kinds: `number`, `boolean`, `select`, `datetime`

- **Spec:** §5.1, §5.2, §3.1 (field registry); §7.2 (projection, `contentHash`).
- **Scope:** `packages/schema/src/fields/`: four kinds with lenient draft and strict publish validators, projection, delivery-type codegen and registry entries. `datetime` is an ISO string with offset; `select` takes a fixed list of values and labels; `number` takes optional `min`, `max`, `integer`. Fixtures in `modules/demo` for each kind (`modules/labak` unchanged).
- **Not in scope:** editor inputs (M2-07).
- **Acceptance:** schema tests per kind (draft accepts empty required, publish refuses it; out-of-range and wrong-type values refused; projection and `contentHash` stable under key order); `codegen` snapshot shows the new delivery types; `pnpm check:slugs` passes.

### M2-04: `reference` field kind

- **Spec:** §5.2, §4.3 (`_ref` and `draft_refs`), §6.2 step 5, §7.1 (references resolve to `{id, type, slug, title, path}` or `null`), A13.
- **Scope:** `packages/schema`: `reference({ to: [types] })` with the standard `_ref` shape; strict validator refuses a target of another type; projection resolves through the worker's projection context to the summary or `null` when unpublished; delivery types mark it nullable. Worker projection context extended only as needed (`apps/cms/src/privileged/worker/projection-context.ts`).
- **Not in scope:** editor picker (M2-08); database changes (the refs trigger and `worker_commit_publish` already check same-tenant, published targets).
- **Acceptance:** unit tests for validation and projection; an integration test on the local stack: publishing an entry that references another tenant's entry is `failed_validation`, one that references an unpublished entry is refused, and unpublishing a referenced entry succeeds and the next release resolves the reference to `null` (§8.5 Delivery row); `pnpm db:test` unchanged and green.

### M2-05: Schema evolution core: transforms and upcasting

- **Spec:** §5.1 (`version`, `transforms`), §5.3, §7.1 (build step "upcast to current schema versions").
- **Scope:** `packages/schema`: `version` and `transforms: { n: fn }` on a type; `upcast(data, fromVersion)` applies `n → n+1` in order and refuses a gap; unknown keys stripped on save, tolerated on read. Release build upcasts each revision before strict validation (`apps/cms/src/privileged/worker/build-release.ts`). The worker's existing outdated-draft refusal returns a distinct, named error code.
- **Not in scope:** the draft migration command (M2-13), editor handling (M2-14), the snapshot check (M2-18).
- **Acceptance:** unit tests: chain of two transforms, missing transform refused, revisions never rewritten (the build reads, upcasts in memory); an integration test on the local stack: a revision at version 1 of a demo test type is delivered at version 2 after a transform; publishing a draft at the old version fails with the named error.

### M2-06: `list` and `group` field kinds

- **Spec:** §5.2 (`list` of any field kind, reorderable; `group`), §4.3 (`_ref` at any depth), A13.
- **Scope:** `packages/schema`: `list(of, { min, max })` and `group({ fields })`, recursive validation, projection and codegen; references and images inside lists resolve like top-level ones; list items carry a stable `_key` for reordering.
- **Acceptance:** unit tests for nesting (list of group of image and reference), `contentHash` changes when items are reordered; an integration test: a `_ref` inside a list inside a group is extracted into `draft_refs` and checked at commit (cross-tenant target refused).

### M2-07: Editor inputs for the scalar kinds

- **Spec:** §5.2, §2.1 (generated form), §10.1.
- **Scope:** `apps/cms/src/editor/form/fields/`: inputs for `number`, `boolean`, `select`, `datetime`, wired through the field registry; accessible labels, help and errors as in Task 31's design; draft copy in `i18n/is.ts`.
- **Acceptance:** component tests (jsdom) per input: value round-trip, required marker, error display, keyboard operation; autosave sends the typed value. Playwright spec added for local acceptance.

### M2-08: Editor input for `reference`

- **Spec:** §5.2, §4.5 (reads under RLS).
- **Scope:** a picker that lists entries of the allowed types in the editor's own tenant through the existing editor views (no migration), shows title and status, and stores `{ _ref }`; a published-only hint when the target is unpublished.
- **Acceptance:** component tests; an integration test with the editor's session: the picker's query for tenant A returns no tenant-B entries, and a non-member gets none.

### M2-09: Singletons and editor structure

- **Spec:** §3.2 (`structure`: groups, order, singletons), §10.1 (singletons).
- **Scope:** `packages/schema/src/module.ts`: `structure` gains groups, order and a `singleton` flag per type; the editor navigation follows it; opening a singleton type opens its one entry, creating it on first open. Database uniqueness of a singleton is **not** decided by the spec (open question 3): the task enforces it in the server action and adds a migration only if Einar has answered; that migration makes the task `security`.
- **Acceptance:** module tests (structure validates: unknown type, duplicate type refused); component tests for the navigation; an integration test: two concurrent first opens of a singleton end with one entry, or the documented limitation if open question 3 is unanswered.

### M2-10: Entry list: title search and status filter

- **Spec:** §10.1 ("list views by type with title search and status filter"), §10.2 (no full-text search or GIN indexes).
- **Scope:** the entry list filters by title (case-insensitive substring) and by status (draft, published, changed since publish, unpublished, archived), with the state in the URL. Uses `api.entry_list`; if the view lacks a needed column, one migration adds it (then `security`), listed in the pull request.
- **Acceptance:** component tests; an integration test with editor sessions: search and filter return only the editor's tenant's entries; `pnpm db:test` catalog tests still pass (the view stays `security_invoker`).

### M2-11: Conflict resolution

- **Spec:** §5.5 ("The editor shows that someone else changed the entry and offers reload; local changes are kept until resolved").
- **Scope:** on a stale save the form keeps the editor's values, shows the newer version's changed fields next to them, and offers "reload theirs" and "keep mine" (a versioned save on top of the newer version). Replaces M1's basic message.
- **Acceptance:** component tests; an integration test: two sessions edit one entry, the second save is rejected, "keep mine" saves at the new version, nothing of either edit is lost silently.

### M2-12: Focal point and alt-text editing

- **Spec:** §5.6 ("focal point and default alt text per asset; alt text per use"), §7.1 (projection).
- **Scope:** complete what M1 started in `ImageField`: per-asset focal point and default alt text editable from the field and from an asset detail, saved through `api.update_asset`; per-use alt overrides the default (existing projection rule); focal point projected into the bundle if the spec's projection names it (open question 4). A migration only if `update_asset` cannot store a value the spec requires (then `security`).
- **Acceptance:** component tests (keyboard-operable focal point, visible focus ring: the Task 31 r3 Minor); an integration test: an editor of tenant B cannot update tenant A's asset (existing persona cell, re-asserted through the new action).

### M2-13: Draft migration command

- **Spec:** §5.3 ("On deploy, a migration script applies transforms to all drafts of that type, each as a normal versioned draft update"), §9.1 (`tools/cli`), §8.2 (secret key only in the CLI and the CMS server).
- **Scope:** `tools/cli`: `cms migrate-drafts --tenant <slug> --type <name>` upcasts every draft below the current version as a versioned update; idempotent; a draft changed meanwhile is retried once, then reported. Runs against the local stack in tests; reads its key the way existing CLI commands do. No hosted run.
- **Acceptance:** CLI tests on the local stack: 3 outdated drafts are migrated, a second run changes nothing, a concurrently edited draft is reported, revisions are untouched (row counts and hashes).

### M2-14: Outdated drafts in the editor

- **Spec:** §5.3 ("A draft can only be published at the current schema version. The worker rejects an outdated draft with a clear error").
- **Scope:** the editor detects a draft below the current version, shows a clear Icelandic notice, and offers to update it (upcast and versioned save); publishing an outdated draft shows the worker's named error from M2-05 in plain words.
- **Acceptance:** component tests; an integration test: open an outdated draft, update it, publish succeeds.

### M2-15: Editor inputs for `list` and `group`

- **Spec:** §5.2 (`list` reorderable, `group`).
- **Scope:** list input with add, remove and reorder (keyboard reorder as well as drag), group input rendering nested fields through the registry.
- **Acceptance:** component tests: reorder by keyboard, nested validation messages point at the right item; autosave of a reordered list.

### M2-16: Restore from a revision

- **Spec:** §5.5 ("Restore from a revision copies its data into the draft (a normal versioned save). Revisions are never modified"), §7.1 (per-entry rollback), §4.5.
- **Scope:** a revision history per entry (published revisions, newest first, with who and when); restore copies the revision's data, upcast to the current version (M2-05), into the draft through `api.save_draft`; then a normal publish. No migration: members already read `revisions` under RLS; if one proves necessary, stop and report.
- **Acceptance:** an integration test on the local stack: publish v1, edit and publish v2, restore v1, publish: the release carries v1's content with a new `revisionId`; revisions unchanged; an editor of tenant B cannot read or restore tenant A's revision.

### M2-17: Session expiry loses no work

- **Spec:** §13.2 M2 criterion "session expiry loses no work"; §4.4 (auth), §5.5.
- **Scope:** when autosave fails because the session expired, the form keeps the values, keeps unsaved changes in the tab (`sessionStorage`, cleared on save and on sign-out, never `localStorage`), shows a sign-in prompt, and after sign-in in another tab (cross-device sign-in from M1) saves at the expected version or goes through M2-11's conflict flow.
- **Acceptance:** component tests with an expired-session response; an integration test: expire a local session (short JWT expiry in a test config, or a revoked refresh token), keep editing, sign in again, the save lands with all edits; sign-out clears the stored copy.

### M2-18: Schema snapshot check in CI

- **Spec:** §5.3 ("CI compares each module's schema snapshot with the previous one and fails on a breaking change without a transform"), §8.5 (Schema tests).
- **Scope:** a committed snapshot per module (types, versions, fields with kind and options); `pnpm check:schema` fails when a type changes incompatibly (rename, removed field, new required field without default, kind change) without a version bump and transform, and when a field name is reused with another kind; an `--update` mode for intentional changes. **This task changes `.github/workflows/ci.yml`** (one step in the `lint` job) and `package.json` (the script).
- **Acceptance:** tests over fixture modules: additive change passes, each breaking change fails with a message naming type and field, breaking change with transform and version bump passes.

### M2-19: Icelandic copy throughout

- **Spec:** §10.1 ("Icelandic editor interface"), §3.2 (`locale`).
- **Scope:** every user-facing string in `apps/cms` comes from `i18n/is.ts`; a test fails on a hard-coded string in editor components (JSX text and `aria-*`/`title` literals) and on unused or missing keys. All new strings are drafts for Einar, listed in the pull request in one table.
- **Acceptance:** the test above; full checks green.
