# Litljómi CMS Hub: M0–M1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task by task (chosen by Einar on 2026-11-01), following the "Execution protocol" section below, which adds to that skill's process. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the M0 foundations and the M1 vertical slice of Litljómi CMS Hub: the complete database security boundary, plus one thin, working path through sign-in, editing, publishing, release delivery, site revalidation and content-specific live confirmation, for two tenants (`labak` and `demo`).

**Architecture:** One Next.js CMS app over one Supabase project. Editors write only through `SECURITY INVOKER` functions in the exposed `api` schema, over tables in the unexposed `cms` schema, with RLS on every table. A privileged worker in the CMS app validates and commits publish requests, builds immutable per-tenant release bundles in Supabase Storage, and confirms that each site renders the new content. Sites read releases through an SDK and never hold Supabase credentials.

**Tech stack:** Node 22, pnpm workspaces, Turborepo, TypeScript (strict), Next.js 16, React 19, Supabase (Postgres 17, Auth, Storage, Vault) with the Supabase CLI, pgTAP, Zod 4, Tiptap (MIT core only), Vitest, Playwright, ESLint 9, GitHub Actions.

**Spec:** `docs/architecture.md` in the new repository. Until the repository exists, it is `project/2026-11-01-litljomi-cms-hub-v1-architecture.md` in the LABAK workspace. **The spec is the source of truth.** Section references (§) in this plan point to it. If this plan and the spec disagree, the spec wins; stop and report the conflict instead of choosing.

## Global constraints

Copied from the spec. Every task's requirements include these.

- v1 contains **no `SECURITY DEFINER` functions** (§4.2).
- `api` is the only exposed schema. It contains only `SECURITY INVOKER` functions and `security_invoker` views. `cms` and `private` are not exposed (§4.2).
- Every function sets `search_path = ''` and schema-qualifies every name (§4.6).
- `EXECUTE` is revoked from `PUBLIC` globally through default privileges, not per schema, and granted per function (§4.5).
- **Never** apply Supabase's custom-schema `GRANT ALL` recipe to `cms` (§4.2).
- Grants for `authenticated` on `cms` are exactly the table in §4.5, per column where it says so.
- Every tenant table has `tenant_id NOT NULL`, and every foreign key between tenant tables is composite with `tenant_id`. Tenant tables: `memberships`, `entries`, `drafts`, `revisions`, `draft_refs`, `revision_refs`, `assets`, `publish_requests`, `releases`, `sites`, `site_deliveries` (§4.3).
- Reference shape inside JSON: `{ "_ref": "<uuid>", "_kind": "entry" | "asset", ... }` (§4.3).
- `drafts.data` is a JSON object of at most 1 MB (§4.3).
- `revisions` and `audit_log` have no `UPDATE`/`DELETE` grant for `anon`, `authenticated` or `service_role` (§4.3, §4.5).
- The Supabase secret key is used only under `apps/cms/src/privileged/**` and in `tools/cli` (§3.1, §8.1).
- Single membership role `editor` (§4.3).
- Accepted uploads: JPEG, PNG, WebP; maximum 20 MB (§5.6).
- Bundle `cache-control: public, max-age=31536000, immutable`. Pointer `cache-control: public, max-age=30` (§7.2).
- Webhook signatures: HMAC-SHA256, timestamp tolerance 5 minutes (§7.3).
- Live check: poll about every 3 seconds, up to 60 seconds (§7.4).
- Editors sign in by email only; password sign-in is refused by the `private.passwordless_access_token` Auth hook, and email changes need both addresses to confirm (§4.4, decisions 18 and 19).
- Editor interface text is Icelandic (§3.2).
- Tiptap: MIT-licensed core packages only, no Pro extensions (§5.4).
- Node 22, Next.js 16, pnpm, Zod 4, Vitest, Playwright (confirmed by Einar).
- Repository: private `einar6969/litljomi-cms`, local path `/Users/einarzoega/litljomi-cms` (confirmed by Einar).
- Execution: local Claude Code with subagents (confirmed by Einar on 2026-11-01), in Auto, Accept-edits or Manual permission mode, never bypass-permissions mode (Einar, 2026-11-01; Auto mode permitted later the same day). A permission mode never authorizes a G1–G7 action. Changes to `.claude/**` need Einar's approval of the exact diff; a permission denial or sandbox refusal is reported, never worked around.

### Per-task loop

1. The controller records the task as `in_progress` in `state.json` (`node tools/harness/state.mjs start <task>`, which checks the task's `dependsOn` and that its lane has no other active task).
2. A fresh implementer, on the model of the task's risk tier, completes the task's steps, including the failing-test-first steps and the commit. The controller records the commit hash.
3. **Reviews by risk tier** (below): for high, spec-compliance and security reviews in parallel (both are read-only and have distinct scopes); for medium, a security review in parallel with one combined spec-and-quality review; for low, one combined spec-and-quality review, plus a security review only if the task touches the security boundary: the controller checks each low-tier diff (and each fix diff) against anything the 14-item security checklist covers (including SQL, grants and policies, authentication, secrets, storage, webhooks and markers, tenant derivation in functions, editor text about cache removal, `.claude/**` and `tools/harness/plan-index.json`) and adds a security review when any is touched. Each report is saved verbatim to `docs/execution/reviews/<task>-<kind>-<round>.md` and recorded in `state.json`. Every finding is rated Critical, Major or Minor, and a review passes when it has no open Critical or Major finding (see "Findings, deferred Minors and escalation").
4. Any Critical or Major finding goes to a **fresh** implementer with the report attached. After the fix, the reviews of that round run again with fresh reviewers, because a fix for one can affect the other. **From round 2 a reviewer checks only the fix:** it receives the fix diff, its own earlier findings and the task text, and checks that each finding is resolved and that the fix introduces nothing new. A full re-review runs only if the fix is large or the security reviewer asks for one. **Every fix commit on a task whose tier requires a security review gets a security re-review of its diff**, whichever review found the issue (a quality fix included); `state.mjs done` refuses when the latest security review is older than the latest recorded commit. Minor findings do not block: the controller records each in `docs/execution/deferred-minors.md`. **A task whose tier requires a security review is not complete until it passes.** If the third round of a review still has a Critical or Major finding, the controller stops and escalates to Einar instead of starting a fourth round.
5. For high-tier tasks, only after both pass, the **code-quality review** runs, under the same rules. A code-quality fix that touches security-relevant code (anything the security checklist covers) sends the task back to step 3.
6. During fix rounds the implementer runs the targeted tests. Once per task, after the reviews pass, the controller runs the whole local suite (`node --test "tools/harness/__tests__/*.test.mjs" && pnpm lint && pnpm typecheck && pnpm check:slugs && pnpm test && pnpm db:reset && pnpm db:test && pnpm test:integration`, plus the task's e2e tests where they exist; only the commands that exist so far) and checks the result itself. It runs it again after every lane merge.
7. The controller marks the task `done` with `state.mjs done <task>`, which refuses unless the reviews the task's tier requires have passed and no recorded review failed. The task's state, its notes and all its review reports go into **one state commit at completion**; there are no per-round record commits. At most one implementer works in each lane at a time.

### Findings, deferred Minors and escalation

Decided by Einar on 2026-11-02, in chat: "I agree that we should simplify the review process: Critical and Major findings block progress, Minors can be deferred, and unresolved issues should be escalated after three review rounds. Independent security reviews remain mandatory." It applies from Task 4 on.

- **Ratings.** Every finding of every reviewer is rated:
  - **Critical:** breaks a security boundary or an architecture guarantee (§8.1, the Global constraints), exposes or loses data, or leaves the change not working.
  - **Major:** a requirement of the task text, the spec or a decision is not met; behaviour is wrong; a required test is missing or cannot fail; or a security weakness short of Critical.
  - **Minor:** affects no correctness, security or stated requirement: wording, naming, readability, diagnostics, test robustness, small refactors.

  A reviewer unsure between two ratings picks the higher and says why. The controller does not lower a rating; a disputed rating goes to Einar.
- **Threat model: the site author** (Einar, 2026-11-02, decision 41.3: "Litljómi, as the author of every site, is trusted."). A finding that needs hostile markup or code written by the site's author (Litljómi) is rated Minor.

It stops only for a gate, a contradiction with the architecture, a sandbox or network change, a new dependency from outside npm, or an escalation after three rounds.

A Minor is cleared by its owning task, whose implementer receives the rows it owns, or reviewed at the next checkpoint. A fix round that is already fixing a Critical or Major finding may also fix Minors in the same files.
- **Escalation.** Rounds are counted per review kind per task (`round` in `state.json`). If the third round of a review still has a Critical or Major finding, the controller blocks the task (`state.mjs block`) and escalates to Einar with the open findings, instead of starting a fourth round. ### Security-sensitive tasks

Tasks **0** (execution setup), **4–12** (database boundary), **17** (privileged zone), **18** (webhook signing and markers), **19–21** (publishing worker), **22** (authentication), **24** (uploads and storage), **25** (publish actions), **26–27** (site revalidation and markers), **28** (hosted configuration), **30** (worker recovery), **32** (sign-in).

**Security review checklist.** Every item applies where relevant to the task. The reviewer reports each one as pass, fail or not applicable, with evidence. An item fails only for a Critical or Major finding; a Minor is reported under the item without failing it:

1. No `SECURITY DEFINER` function exists. Every function has `search_path = ''` and schema-qualified names.
2. `cms` and `private` are not exposed. `api` holds only invoker functions and `security_invoker` views.
3. Grants for `authenticated` and `service_role` match §4.5 exactly, including the per-column grants. `anon` has nothing. `EXECUTE` is not granted to `PUBLIC`.
4. RLS is enabled on every `cms` table. Tenant policies check membership against the table, per request. Console policies require `aal2`. Content tables have no platform-admin clause.
5. Every tenant table has `tenant_id NOT NULL` and composite tenant foreign keys.
6. Functions derive the tenant from the data whenever an ID determines it, and never trust a tenant parameter for authorization.
7. `worker_*` and `admin_*` are executable only by `service_role` and check authorization explicitly.
8. The commit copies data from `cms.drafts` inside the transaction, checks version and schema version, re-checks membership and tenant status, and locks referenced rows.
9. Withdrawal precedence: release content is decided only by the database's current published state.
10. The secret key appears only under `apps/cms/src/privileged/**` and `tools/cli`. No secret is committed, logged or sent to a client or site.
11. Live confirmation uses entry markers with the new content hash, rendered next to the entry's content. A release marker is never treated as proof.
12. Editor text never promises removal from third-party caches.
13. Anything that contradicts the spec is reported as a contradiction, not fixed by the reviewer.
14. The diff does not change `.claude/**` (permission settings and agent definitions) unless the task is Task 0 or Einar approved that change, and it widens no permission or sandbox setting without that approval.

### Decisions and contradictions

- Implementers and reviewers **do not make architectural decisions.** If a step is ambiguous, conflicts with the spec, or cannot work as written (including a failed validation gate), the subagent stops and reports to the controller.
- The controller decides only if the answer is already fixed by the spec, this plan's decisions, or an earlier answer from Einar. Otherwise it stops and asks Einar.
- Interfaces are produced by one task and consumed by later ones. No subagent changes an interface produced by an earlier task; that goes back to the controller.
- At most one implementer per lane at a time, each task starting only when its `dependsOn` tasks are done ("Execution order"). Through Phase 0 and Task 4, one implementer at a time.

## Implementation-level decisions made in this plan

These fill gaps the spec leaves to the builder. None changes a spec decision.

1. **GraphQL is disabled** (`drop extension if exists pg_graphql`). The Hub does not use it, and dropping it removes a surface. A1 still tests the endpoint.
2. **Slugs** must match `^[a-z0-9]+(?:-[a-z0-9]+)*$`, enforced by a check constraint. Icelandic characters are transliterated in the editor (þ→th, ð→d, æ→ae, ö→o, á→a, é→e, í→i, ó→o, ú→u, ý→y). This matches the LABAK repository's existing slug rule ("lowercase ASCII with hyphens").
3. **Errors from `api` functions** use `raise exception` with SQLSTATE `P0001` and one of these messages: `version_conflict`, `not_found`, `slug_locked`, `slug_taken`, `forbidden`, `invalid_reference`, `published_reference`, `tenant_inactive`. Integrity checks enforced by constraints and AFTER triggers raise their own SQLSTATEs, which the editor maps to a generic error: `23514` for check constraints and the AFTER checks (`drafts.version must increase by exactly 1`, `<table>.<col> must equal auth.uid()`, write-once `first_published_at`), `23503`/`23505` for keys, `22P02` for a malformed `_ref`, `54000` for the reference-extraction limits (decisions 27–29). ## Exactness: what M1 proves (agreed with Einar)

For every committed publish request, the tests prove:

1. The revision's `data` equals the `drafts.data` that was validated, its `draft_version` equals the validated version, and its `schema_version` equals the validated schema version.
2. The revision's `revision_refs` equal the draft's `draft_refs` at that version.
3. Every reference was valid at commit: same tenant, entries published, assets not archived. The referenced rows are locked (`FOR SHARE`) during the commit, so a concurrent unpublish or archive is serialised with it.
4. Referenced entries' displayed fields are resolved from the current published state when the release is built (§7.1). They are not frozen at commit.

## Withdrawal and failure visibility

- **Withdrawal is best-effort beyond our own storage.** Tests prove the absence of content in our buckets and on the declared site pages only. No editor text or document may promise removal from CDN, browser or search-engine caches.
- **Fail-closed delivery errors must be visible and actionable.** In M1, an entry left out of a release is recorded in `releases.error`, shown to the editor as "delivery failed", and alerted (decision 10). In M1, before the M3 fallback rule exists, a regression can remove a previously live entry from a staging site. That is expected and must be reported, not hidden. Rebuilding is possible in M1 by re-running the worker on the tenant (Task 20 exposes `buildRelease(tenantId)`); the operator command comes in M4.

## Review focus

Failure modes the spec implies that no milestone criterion names. Each has a test in its owning task.

1. **Session expiry during autosave.** The save fails with an auth error; the editor keeps local changes and asks the user to sign in again, without losing work. Test: Task 23.
2. **Pasting from Word or the web** with tables, colours or disallowed nodes. Unsupported content is stripped, and the saved document validates against the v1 rich-text schema. Test: Tasks 14 and 24.
3. **Pressing publish while an autosave is in flight.** The request carries the version the editor last saw; if the draft moved on, the worker marks the request `superseded`, and the editor is told to publish again. Test: Tasks 19 and 25.
4. **Unsupported or oversized images** (HEIC, PDF, over 20 MB). They are rejected in the editor before upload, and the database refuses an asset row with another MIME type. Test: Tasks 8 and 24.
5. **Icelandic titles turned into slugs, and slug collisions.** `Brauð ársins 2025` becomes `braud-arsins-2025`; a duplicate slug in the same tenant and type gives `slug_taken`, while the same slug in another tenant is allowed. Test: Tasks 6, 13 and 23.
